D. 根本課題

R-1. 満願（108枚）到達に、見せ場が無い

確信度: high — 3系統の証拠が一致: ①自動プレイで108枚を跨いだ瞬間の window.__se.counts（whiff/end）がともに変化なし、②同瞬間のcanvasスクリーンショットに浮き文字・鐘の視覚効果が写っていない、③コード読解（src/game.js の purify()）で、SE「end」と浮き文字が発火するのは曲の一巡完了かつ次曲の最低枚数（90/200/300/430/560）到達時だけで、108はどの閾値とも一致しないため、この経路では絶対に発火しない構造だと確認できる。加えて docs/DEVELOPMENT.md 2026-09-02の引き継ぎ節が「満願の見せ場…この作業は残っていない」と自ら記録している。

因果連鎖: SPEC §4「見せ場」の行は「節目（108の倍数）ごとに…鐘＋浮き文字」と書かれているが、その後の改訂（曲が替わる夜）で節目の仕組みそのものが「108の倍数」から「曲の一巡＋最低枚数」へ置き換わった → 108という数はもはやどの発火条件とも結びついていない → 満願は結果画面の称号テキスト（「称号：満願」）を読むまで、プレイヤーに伝わる手段が無い。

根拠: O-07（B-7）。反証: 「満願はゴールではなく、延長が本編」という設計思想（DEVELOPMENT.mdにオーナー発言として記録あり）に立てば、節目を強調しすぎない方が良い、という見方も成り立つ——ここは実装不備ではなく企画判断の余地がある点として、解釈は分析の外に置く。

R-2. README「番付」節が実装と食い違う

確信度: high — 直接比較: README「送る点は合成値 段×100+従の軸」「ボードはmain」に対し、src/game.js:13 は RANK_BOARD='main_v1'、reportScore()（277-279行）は purified（浄めた枚数そのもの）をそのまま渡しており桁の合成をしていない。docs/SPEC.md §7-a「合成値＝浄めた枚数そのもの。桁の細工はしない（前作のような『段×100+浄化』は要らない）」と実装は一致しており、ずれているのはREADMEだけ。あわせてREADME「遊び方」節の3行が「（タップで何が起きるか）」等の未記入プレースホルダーのまま残っている。

R-3. 入力解禁の瞬間、帳はまだ完全には開ききっていない（実害は小さい）

確信度: medium（影響は小） — 実測: 入力解禁時刻（1500ms）における door-l/door-rの残り幅は左右各26px（画面幅390pxの6.7%）。SPEC本文「開ききるまで叩けない」を厳密に読むと一致しない。ただし #door は pointer-events:none と明記されており、この残り幅がタップの成否に影響することは無い。1900ms前後にはほぼ完全に消える（残り-1px）。

因果連鎖: begin() の pausedUntil = performance.now() + 1500（入力解禁）と、帳のCSSトランジション（openクラス付与から1.5秒・付与自体はbegin()から500ms後）が、独立した2つの数値として設計されている → 500ms（帳の起動遅延）ぶんだけ、入力解禁が帳の「起動から1.5秒後」より早く訪れる計算になる（実測もこれと整合）。

根拠: O-02（A-2）。反証: 実測上、影響が見えるのは画面の左右端26pxのみで、盤面中央のレーン1・2は1500ms時点で完全に見えている。人が違和感を持つかは未実施（inferred）。

R-4. 記録がある人の0枚は番付へ送られる（課題ではなく、把握しておく事実）

確信度: low（課題かどうかは未確定・意図された設計） — 実測: 記録が一度も無い状態での0枚は submitScore 0回。事前にbest=15を仕込んだ状態での0枚は submitScore 1回（score 0）、結果画面に順位行も出た。canSubmitScore() のコメント「記録が無い人の0だけ送らない（宵あらわし式）」、README「送らない経路: 一度も記録が無い人の0段の夜」とも、実測はそのとおりに一致する。

因果連鎖: 意図された設計であり、シリーズ内の「宵あらわし」と同じ規則を踏襲している。ここでは「番付に0の行が積まれうる」という事実だけを記録に残す。

根拠: O-11（E-12）。
