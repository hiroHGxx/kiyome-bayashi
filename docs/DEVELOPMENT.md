作った順に、踏んだ穴と直し方を残す。仕様は `SPEC.md`、シリーズ共通は `kitan-works/docs/`。

## 2026-09-01 骨を生やした（kitan-scaffold）

- 雛形の決めごと（案内カードの時間割・safe-area・束保存・送る守り・build の安全弁）はそのまま。外したものがあればここに理由を書く

## 2026-09-01 第1便（札絵58枚・遊びの芯・実測）

### 札絵は「組み立てたパス」だと artifact で消える

`build-dist.js` は **HTML／JS の中に文字列として書かれた素材の道**を正規表現で拾って base64 に差し替える。
札絵の道を `"assets/art/fuda/" + id + "_" + st + ".webp"` のように**組み立てて**書くと、正規表現に当たらない。
index.html（Pages）は相対パスのまま動くので気づかず、**artifact だけ札が全部出ない**という壊れ方をする。

→ 直し方: **58枚ぶんの道を `FUDA` という定数の表に、文字列のまま並べて置く。**参照は `FUDA[id+"_"+st]`。
表は `scripts/data/spirits-table.json` から機械で起こす（手で書かない）。
あわせて `build-dist.js` の正規表現が `assets/art/` の**1階層下まで**しか見ていなかったので、
`(?:[\w.-]+\/)*` を足して `assets/art/fuda/xxx.webp` を拾えるようにした。差し替えが58件あることを毎回数える。

### 骨の数字は、遊びを替えたら必ず矛盾する

雛形（kitan-scaffold）は「段を積む」型の数字が焼いてあった。遊びを落下タイルに替えたので、
**放っておくと静かに壊れる**箇所が3つあった。番付そのものは別便だが、数字だけは合わせた。

- `MAX_FLOOR = 80`: 束から読む値の上限。**81枚以上の記録が読み込み時に捨てられる。**→ `MAX_KEEP = 99999`（枚数は青天井）
- `SCORE_DIGIT = 100`（合成値 段×100+従）: この作の点は **枚数そのもの**（SPEC §7-a）。番付の札の表示も「n段（m）」のままだった → 「n枚」
- `TITLES` の閾値が段位（0/8/24/48/80）のまま → 枚数の目盛りへ。**文言は仮**（意匠・文章の便で決め直す）
- board 名も `main` → `main_v1`（SPEC §7-a）。**まだ一度も送っていないので、いま替えるのが唯一ただの時**

### VMAX は「満願を通す」テストでは決まらなかった

受け入れ基準は「自動プレイが108枚を通せること。`VMAX` はこの実測から決める」だったが、
測ってみると **108枚時点の速度は 277px/秒**で、`VMAX=520` には**まったく届いていない**（届くのは214枚＝延長）。
つまり満願の測定は `VMAX` について何も語らない。
→ 延長まで通す口（`#autotest=260`）を足して別に測った: **260枚・164.7秒・例外0で自動プレイは通る。**
残るのは「人が 0.35秒/行に追えるか」だけで、これは実機の宿題（SPEC §11-4）。
**「基準に書いてあるから決まる」とはかぎらない。測って初めて、その基準では決まらないと分かることがある。**

### 実測（自動プレイ・playtest ①、2回とも同値）

- 満願（108枚）まで **96.1秒**（受け入れ基準の 60〜120秒 に入る）。企画の想定「約80秒」は外れた
- 29柱すべてが1回の満願の中で灯る（`pillars: 29`）
- 札絵 58枚 = 952KB（平均16.4KB）／`index.html` 35KB ／ `dist/artifact.html` 1.33MB

### 同じ柱が盤に二枚出る（画面を見て初めて分かった）

自動プレイの実画面を撮ったら、**同じ極彩の札が盤に3枚**並んでいた。検査は全部通っていた
（例外0・満願まで通る）。**「例外が出ない」は「絵が壊れていない」ではない。**

原因は2つあって、1つ直しただけでは消えなかった。**目で見て直し、機械で数えて、まだ11件残っていた。**

1. **色の札の抽選**が「浄めた柱」から素直に引いていた。序盤は浄めた柱が数柱しかないのに、
   盤には最大6行＝12枚が出ている。**引ける数より出ている数のほうが多い**ので必ず重なる。
   → 盤に出ている柱を除く。除いて空になったら**29柱まで広げる**（「色の札は浄めた柱」は遊ぶ側に
   見えない決めごと、重なりは見える。**見える側を優先する**）
2. それでも 496回中11回 残った。**闇の札の抽選**が29柱の山から順に配るだけで、盤を見ていなかった。
   一巡の終わりぎわは山の残りが数柱で、その全部が盤に出ていることがある。
   → 闇も盤に出ている柱を飛ばす。飛ばせなくなったら**次の一巡を前倒しで足す**。
   → 496回中 **0件**。

**この手の穴は「絵が出ているか」を見るテストでは捕まらない。**盤の中身（どの柱が同時に出ているか）を
通しで覗いて数える検査を `playtest.js` に足した（200msごとに約500回）。**目で見つけた欠けは、機械で数える形にして残す。**

### この便で入れていないもの（宿題）

音（§5）／満願の見せ場・結果札・図鑑の作り込み（§4）／束に `clears`・`spirits` を持たせる（§7）／
`VMAX` の実機判断／OGP・README の本文。

**意匠の便へ申し送り**（この便では触っていない）:

- **canvas が上下に letterbox する。** `fitCanvas` は 480×720 を縦横同率で縮めるので、390×844 の端末では
  盤の上下に 76px ずつ余る。SPEC §1 は「論理480×720 を**最小に高さは伸びる**」と書いているので、
  **仕様と実装がここだけ食い違っている**。骨（kitan-scaffold）の `fitCanvas` をそのまま使った結果なので、
  外すなら意匠の便で。伸ばしても満願の秒数は変わらない（速度と行高だけで決まる）が、先読みできる行数は増える。
- 「満　天」「満　願」の浮き文字が、極彩の札の上に出るので読みにくい。地を敷くか、出す場所を選ぶか。

## 2026-09-02 意匠の第一段（印・盤の高さ・浮き文字）

**この段は見張り役（主のセッション）が自分で手を入れた。**意匠の担当を2度立てたが、
どちらも通信エラーで**1行もコミットせずに落ちた**。範囲を4件→3件に狭めて立て直しても同じだったので、
「誰も見ていない時間に進む」という委譲の目的が果たされていないと判断して切り替えた。
**規則（実装は担当に投げる）から外れた判断なので、理由をここに残す。**

### 1. 闇の札の印が実機寸法で見えていなかった（不具合）

- 症状: 390×844・DPR2 の実写真で、盤に出ている**3枚の闇の札のうち2枚しか枠が判別できない**。
  2倍に拡大して初めて3枚とも出ていると分かった。
- **コードは正しかった**（`!r.cleared` で必ず描いている）。**正しく描かれているのに、見えていない。**
  `2px`・不透明度 `.55` が、実寸では 1.6 CSS px の薄い線にしかならなかった。
- 直し: 金泥 `#D9A94C` の **6px** ＋ 内側に宵闇 `#131320` の **2px**。
  内側の暗い線は**絵の明るい柱でも金の縁が溶けない**ようにするため——
  **特定の暗い柱に手当てをせず、印そのものを全札に効く形で直す**（第4弾の教訓）。
- あわせて元の `rgba(212,175,55,.55)`（＝`#D4AF37`）は **`data/design-tokens.json` に無い値**だった。
  仕様を書いた側の誤り。**知っている16進ほど、系を確かめずに手が出る。**

**学び: 「拡大したら見えた」は「見えている」ではない。**
実機寸法の写真で判断がつかなかった時点で、それが既に「見えない」という答えだった。
**拡大は原因を追うときだけに使う。**検分の拡大率を上げると、見えない不具合を自分の目で塗り潰す。

### 2. 盤の高さは伸ばさない（仕様の側を直した）

第1便の申し送り「`fitCanvas` が letterbox する・SPEC §1 の『高さは伸びる』と食い違う」への裁定。
**伸ばさない方を正とし、SPEC §1 を直した。**理由は**番付の公平さ**——
高さが端末で変わると、**背の高い端末ほど先の行が見えて易しくなる**。
全国の番付で枚数を競う作なので、盤は誰の端末でも同じでなければならない。

**食い違いは「実装を仕様に合わせる」とはかぎらない。**仕様の方が浅いこともある。

### 3. 浮き文字に縁取りを敷いた

「満　願」「満　天」が単色 `#F0CE7E` で、段10 の極彩色の札に乗ると沈んでいた。
宵闇 `#131320` の縁取り（8px・`lineJoin:round`）を先に敷いてから金を乗せる形にした。

## 2026-09-02 第3便（束の clears・spirits／結果札／図鑑29柱）

### 1. 束に入れ子を持たせるときは「知っている鍵」だけ読む

`spirits`（柱ごとの浄めた数）は束で初めての**入れ子**。`best` のような数値と違い、
**壊れた束・他所の束が来たときに、鍵の数だけ膨らむ**。
→ `mergeSave` は `SPIRITS` の29柱を順に見て、その鍵だけを読む（`Object.keys(o.spirits)` で回さない）。
値は `best` と同じ物差し（0〜`MAX_KEEP` の整数）で、範囲外は**丸めずに捨てる**。

あわせて `persistSave` は `{ ...saveData }` の浅い写しでは足りない。
**入れ子は参照が渡るので、SDK が握ったまま次の夜の加算が混ざる。**`spirits` も写して渡す。

束へ足すのは**夜の終わりに1回**（`showGameOver` の中）。稽古の夜は足さない——
「送らない経路」と「残さない経路」が同じ `!practice` の1か所で決まる形を崩さない。

### 2. 「最高記録を更新」が二重になっていた

結果札に自己最高の行を足したら、番付の1行目（`#final-rank-mark`）と**同じことを二度言う**画になった。
順位の行は SDK の `improved`（番付側の記録）、新しい行は束の `best`（自分の記録）で、出どころが違う。
→ 順位の1行目を「**番付の記録を更新**」に直し、自己最高は新しい行が言う。
**SDK が読めない夜（Artifact・枠の外）でも自己最高の更新が出る**という利点もそのまま。

### 3. 29柱の図鑑は、札ごと送ると閉じられなくなる

図鑑は番付と同じ「開いて閉じる札」（SHITSURAE §7）にしたが、**番付は10行、図鑑は8行×4列**。
`.bz-card` の `overflow-y: auto` をそのまま使うと、**下まで送ったとき ✕ が画面の上へ流れて消える。**
札が画面をほぼ埋めるので**外側タップの余地も無く、閉じる手が両方とも失われる。**
→ 送るのは升目（`#zk-grid`）だけにして、札自身は `overflow: hidden`。✕・見出し・「n／29 柱」は残る。

**同じ型を写すときは、型が前提にしていた量を確かめる。**この穴は行数が増えて初めて出る。
検査（playtest ①）に「下まで送っても ✕ が見える」を数える形で残した。

### 実写真で確かめた寸法（DPR2）

| 画面 | 結果札 | 「もう一夜」の下端 | 図鑑の札 |
|---|---|---|---|
| 390×844 | 463px | 625px | — |
| **375×667**（天井の検分） | 381px | **509px**（画面667） | 643px（上限655）・名前12px |

順位2行＋図鑑の入口を足しても天井は割っていない。図鑑は下まで送っても ✕ が天 23px に残る。

### この便で入れていないもの（宿題）

音（§5）／満願の一斉染めの演出／OGP・README 本文／`VMAX` の実機判断。
図鑑の入口は**結果札だけ**（SPEC §4 のリザルトに置いた）。題字の札からは開けない——
戻ってきた人が遊ばずに集めた柱を見に行けないので、入口を増やすかは意匠・企画の裁定を待つ。
